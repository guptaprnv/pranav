# Open Risks: Model, Agent, and Data Perspective

A structural gap-check across [`product-architecture.md`](../product-architecture.md) and the companion engineering docs — issues that haven't been resolved by the design so far and are worth deciding deliberately, not discovering under load. Two of these (multi-turn compliance drift, prompt injection) are gaps in what's been designed, not just things to keep in mind.

## Model

**Versioning is three axes, not one.** Pipeline versioning (quant formulas, extraction pipeline — see [`data-architecture.md`](./data-architecture.md)) has been established, but a given output also depends on which model version generated it and which system prompt/instructions it was given. All three need to be logged together as what actually produced a claim. This matters concretely because LLM providers deprecate model versions on their own schedule — if "explain what happened 8 months ago" ever needs to reproduce reasoning, the model that did it may no longer exist to re-run, which is why the audit log has to store the actual output, not just enough metadata to regenerate it on demand.

**Evals need to be a regression suite that reruns on every model swap, not a one-time gate.** A provider's "same version" model can behave differently after a silent update; a conscious model upgrade needs the grounding/compliance/fidelity evals (`product-architecture.md`, Section 7, Evals) rerun before promotion, not just at initial build time.

## Agent

**Multi-turn conversations can drift past a boundary that holds fine turn-by-turn — this is a real open question, not resolved by the current design.** Everything designed so far (query router, orchestrator, validation gates — see [`reasoning-agent-architecture.md`](./reasoning-agent-architecture.md)) operates on one query at a time. A retail user asking "what's my rate exposure," then "should I reduce it," then a follow-up referencing both, could have each individual turn pass its compliance gate while the *conversation* accumulates toward personalized advice. The compliance gate as designed checks one narrative at a time; it needs a session-level view too, or a multi-turn conversation can launder its way past a boundary that holds per-turn. Same personalization-boundary problem from the main doc (Section 7), showing up at a different timescale.

**Retrieved content is an unaddressed prompt-injection surface.** The transcript-extraction and news-retrieval steps feed external text directly into model context. Any system doing that has a prompt-injection risk: manipulated or adversarially-crafted content in a source document attempting to steer the model's output, not just noisy or low-quality content. This needs the standard treatment — retrieved text is data, structurally separated from instructions, never capable of redirecting what the model does — applied explicitly at the ingestion points ([`concall-extraction.md`](./concall-extraction.md), news retrieval). The stakes are higher than a typical chatbot: a jailbroken compliance boundary in a licensed RA's published, one-to-many research is a regulatory event, not just a bad response to one user.

## Data

**Raw ingested data needs a source/vendor field, not just computed primitives.** `data-architecture.md`'s storage design puts `computed_at`/`pipeline_version`/`input_as_of` on computed values, but a transcript or news item pulled from a vendor also needs its own provenance tag — which vendor, which ingestion run. Vendors get acquired, change terms, or silently degrade quality; without provenance on the raw data itself, a later vendor swap can't be distinguished from a data-quality regression, and historical citations can't honestly say where they came from.

**SEBI recordkeeping and DPDP user-erasure rights point in different directions if not designed around carefully.** The audit-trail design (immutable, retained per RA recordkeeping) and India's Digital Personal Data Protection Act (which gives users retention limits and erasure rights over personal data) are in tension if user data ends up inside the same retained records. The likely resolution follows from something already decided for other reasons: the personalization-boundary principle (`product-architecture.md`, Section 7) means published theses are supposed to be general, not built from individual user data, so the research audit trail shouldn't contain PII if that boundary actually holds. The user's own holdings data, which does need to be erasable, has to stay architecturally separate from the retained research artifacts — reinforcing the storage separation already proposed for security reasons (`data-architecture.md`, Storage), for a second, independent legal reason. Flagged here as an open compliance question, not treated as already solved.
